# MDX extraction: performance and review

This draft supports live styles in authored MDX without adding a runtime dependency. **It is blocked for merge on
reference-style image handling**, described in the [design note](../mdx-parser.md).

## Measurements

Local macOS arm64 release builds, Rust 1.93.0, baseline `5a26802af`, measured on 2026-10-05. MDX and TSX fixtures
contain the same live styles; MDX also contains prose and fenced examples. These are synthetic in-memory Rust workloads,
not filesystem, Node, Storybook, or WASM build measurements.

Timing and allocation profiling run separately. The `--timing` flag disables allocation counters; heap fields become
`null`. Latencies below are medians across five process runs. Extraction uses 30 warmup calls and 20–300 timed samples,
depending on source size. Mixed builds alternate scenario order over 100 samples per process.

| Timing scenario                                     | Equivalent TSX |       MDX |
| --------------------------------------------------- | -------------: | --------: |
| 1 live style block                                  |        4.00 µs |   5.33 µs |
| 20 live style blocks                                |       34.08 µs |  47.17 µs |
| 200 live style blocks                               |      308.46 µs | 431.08 µs |
| Changed-file update + CSS, 20 blocks                |       69.52 µs |  83.05 µs |
| Fresh 200-file project, replacing 20 files with MDX |       1.349 ms |  1.379 ms |

The mixed-project median paired overhead is **2.37%** across five process runs. The large MDX document is 35,269 bytes;
equivalent TSX is 18,692 bytes. MDX adds about 0.12 ms of extraction and 14 µs per changed-file update on these
fixtures.

A separate ten-run comparison reverses baseline/feature process order on alternate runs. Ordinary TSX paired median
changes are **+1.07% / +0.82% / +1.07%** for 1/20/200 blocks. Baseline and feature allocation counts, total allocated
bytes, and peak heap are identical for those cases. Small timing differences remain subject to local variation.

Memory profiling is a separate run with counters enabled:

| Memory scenario                                | Equivalent TSX |       MDX |
| ---------------------------------------------- | -------------: | --------: |
| Peak tracked heap, 200 blocks                  |      917,810 B | 579,234 B |
| Total bytes allocated, 200 blocks              |    1,166,250 B | 892,582 B |
| Allocation count, 200 blocks                   |          3,875 |     4,510 |
| Peak additional watch heap                     |      110,038 B |  83,594 B |
| Retained heap change after 1,000 changed edits |            0 B |       0 B |

The large MDX fixture uses 37% less peak heap and 23% fewer allocated bytes, while making more small allocations. This
does not imply every MDX file uses less memory. Heap figures are tracked Rust allocations, not RSS or allocator page
retention. Retained change is signed rather than clamped to zero. Watch validation checks that the new color is emitted
and the previous color is removed before timing starts.

## Regression gates

| Gate                                                                                      | Local result                               |
| ----------------------------------------------------------------------------------------- | ------------------------------------------ |
| Investigate repeatable ordinary TSX timing increases above 2%; preserve allocation counts | Within 2%, allocations unchanged           |
| At most 3% added median time for a project with 10% MDX                                   | 2.37% paired overhead                      |
| Below 0.6 ms and below 2× equivalent TSX for the 35 KB / 200-block MDX fixture            | 0.431 ms, 1.40× TSX                        |
| No retained heap growth after 1,000 changed edits following warmup                        | No change observed                         |
| Dense inline JSX should avoid repeated paragraph scans                                    | 100/1,000/4,000 tags: 0.029/0.251/0.985 ms |
| Malformed input should avoid repeated whole-document parses                               | 25/100/400 KB: 0.346/1.333/5.426 ms        |

Dense-tag and malformed-input samples show roughly linear growth; they are not a proof for every source shape. Confirm
these gates on CI and a real documentation project before merging. WASM compiles, but its latency and size are
unmeasured.

## Reproduce

From the repository root:

```sh
cargo build -p pandacss_bench --bin mdx_extract --release --locked
target/release/mdx_extract --timing
target/release/mdx_extract --mixed --timing
target/release/mdx_extract --watch --timing
target/release/mdx_extract --dense-inline --timing
target/release/mdx_extract --esm-stress --timing

# Separate allocation profiles:
target/release/mdx_extract
target/release/mdx_extract --watch

# Compare the same harness on an isolated baseline checkout:
target/release/mdx_extract --baseline --timing

cargo nextest run -p pandacss_sfc -p pandacss_extractor -p pandacss_compiler --locked
```

For the baseline comparison, copy `bench/src/bin/mdx_extract.rs` and its `mdx_extract/` helper directory into a detached
checkout at `5a26802af`, build there with the same release command, and alternate its `--baseline --timing` runs with
feature runs. No raw measurement files are committed.

## Review findings

The review fixed repeated line scans for inline tags, false exclusion after invalid reference definitions, and initial
BOM handling. It separated timing from allocation counting, gave Markdown caches and canvas state explicit owners,
renamed shared Astro/MDX attribute collection, and moved boundary fixtures into named tests with inline snapshots and extracted-value assertions.

Validation: 2,451 scoped Rust tests pass, including existing stylesheet snapshots without changes. The native compiler
suite, workspace clippy, formatting, and WASM check pass. Extraction boundaries match the official MDX parser across 69 distinct focused cases (the original 101 included 32 duplicates)
and 151 repository documents. This establishes coverage of those cases rather than full conformance.

**Known over-extraction limitation:** JSX in a reference-style image label can still emit extra CSS.
Document-wide reference-image resolution remains a follow-up. MDX rewriting and remark/rehype plugin execution remain outside this
feature. See [the ownership and source-offset contract](../mdx-parser.md).
