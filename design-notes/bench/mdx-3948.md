# MDX extraction: implementation and performance

Measured locally on 2026-10-05 on macOS arm64, Rust 1.93.0, release builds, against baseline `5a26802af`. This is an
implementation experiment for [#3948](https://github.com/chakra-ui/panda/issues/3948), not a cross-machine performance
guarantee. The implementation adds no runtime dependencies and retains the existing TSX extraction path.

## Results

Extraction fixtures contain the same live styles and imports. MDX additionally contains Markdown and fenced examples.
Numbers below are medians of five process runs. Each extraction run warms up and measures up to 300 iterations.

| Scenario                                       | Equivalent TSX | Native MDX | Implication                      |
| ---------------------------------------------- | -------------: | ---------: | -------------------------------- |
| 1 live style block                             |        4.17 µs |    5.54 µs | About 1.4 µs extra               |
| 20 live style blocks                           |       35.75 µs |   51.79 µs | About 16 µs extra                |
| 200 live style blocks                          |      330.75 µs |  450.50 µs | About 0.12 ms extra              |
| Peak heap, 200 blocks                          |      917,810 B |  579,234 B | MDX uses 36.9% less              |
| Total bytes allocated, 200 blocks              |    1,166,250 B |  892,582 B | MDX allocates 23.5% less         |
| Allocations, 200 blocks                        |          3,875 |      4,510 | MDX makes more small allocations |
| Update + CSS emission, 20 blocks               |       78.58 µs |   93.61 µs | About 15 µs extra per edit       |
| Peak additional watch heap                     |      110,038 B |   83,594 B | MDX uses 24.0% less              |
| Retained heap growth after 1,000 changed edits |            0 B |        0 B | No growth observed after warmup  |

The large MDX document is 35,269 bytes; equivalent TSX is 18,692 bytes. Smaller peak heap is consistent with dropping
markup from Oxc's input while collecting only attribute spans. This does not imply MDX always uses less memory.

Alternating baseline and feature binaries over five process runs kept ordinary TSX allocation counts, total allocated
bytes, and peak heap identical. Median latency changed by +0.2% (200 blocks), +1.8% (20), and +1.0% (1). Those small
timing differences are within the observed local variation; there is no evidence here of an ordinary TSX regression.

For fresh 200-file projects, replacing 20 TSX files with equivalent MDX pages took **1.413 ms versus 1.381 ms**. The
median paired overhead across ten process runs was **2.55%**. Peak incremental heap was 365,028 B versus 365,968 B. Each
process alternates 100 samples per scenario and reverses their order each round. Earlier separate batches were noisy
(including a 7% aggregate difference); their raw results are preserved rather than treated as a regression. This is an
in-memory Rust project build with a small config, not a filesystem/Node/Storybook build benchmark.

Native binding size grew from 7,969,808 B to 8,002,896 B: **33,088 B (0.42%)** using the same release profile. WASM
compiles successfully; WASM latency and artifact size have not been measured.

## Why the first design was replaced

The initial full Markdown AST prototype took about 7.93 ms on the 200-block fixture, with about 9.7 MB peak tracked heap
and 55.8 MB total allocations. The final scanner takes 0.45 ms: roughly 17.6 times faster on that fixture. The final
adapter does not build a Markdown AST or parse each embedded JavaScript expression. Oxc parses the lowered document
once, and dynamic props do not trigger fallback reparses.

## Expectations and gates

- Existing TS/TSX: aim for no measurable regression. Investigate a repeatable median increase above 2%; allocation and
  peak-heap counts should remain unchanged. This local comparison meets that criterion.
- A 200-file build with 10% MDX: target at most 3% added median time against equivalent TSX. The alternating local
  benchmark meets that target at 2.55%; confirm on CI and a real documentation project before merging.
- MDX extraction: target below 0.6 ms for this 35 KB / 200-block fixture and below 2 times equivalent TSX. Both pass.
- Watch: no retained heap growth after warmup over 1,000 genuinely changed edits. Passes locally. This measures tracked
  live allocations, not OS RSS or allocator page retention.
- Malformed input: growth should follow input size rather than repeated whole-document parses. Repeated unmatched
  expression fixtures at 25/100/400 KB take 0.365/1.441/5.876 ms. Multiline export fixtures at 20/80/320 entries take
  8.29/14.83/40.21 µs. These samples show roughly linear growth, not a proof for every malformed document.

The allocation counter wraps Rust's system allocator and remains enabled during timing. Peak heap measures extra live
allocated bytes during an operation, not RSS, JavaScript heap, or cumulative allocations. Watch tests alternate style
values to avoid measuring unchanged-source cache hits.

## Reproduce and review

From the repository root:

```sh
cargo build -p pandacss_bench --bin mdx_extract --release --locked
target/release/mdx_extract
target/release/mdx_extract --mixed
target/release/mdx_extract --watch
target/release/mdx_extract --esm-stress
target/release/mdx_extract --baseline
node bench/scripts/mdx-parity.mjs
cargo nextest run -p pandacss_sfc -p pandacss_extractor -p pandacss_compiler --locked
```

Raw samples are in `mdx-3948-final.jsonl`, `mdx-3948-final-tsx-baseline.jsonl`, and `mdx-3948-mixed-paired.jsonl`.
`mdx-3948-parser.jsonl` records the discarded AST prototype. Earlier batch measurements are retained in the other
`mdx-3948-*.jsonl` files.

Correctness checks: 2,449 scoped Rust tests passed, including all 838 existing stylesheet tests without snapshot
changes; 787 native compiler tests passed; generated-code framework tests and type checks passed; workspace clippy, Rust
formatting, and the WASM target check passed. A subsequent 809 extractor/compiler tests passed after tightening
malformed entity scanning. Named element and JavaScript call spans match the official MDX parser across 91 focused
fixtures and all 151 repository MDX documents.

The adapter is about 890 lines plus about 160 lines of extraction integration. The main maintenance cost is Markdown
boundary handling. Keep the PR in draft until broader third-party corpora and real-project performance are checked. MDX
rewriting and remark/rehype plugin execution remain outside this experiment. See [the design](../mdx-parser.md).
