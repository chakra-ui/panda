  Panda compiles your design system. Typed tokens and recipes in, atomic CSS out, nothing computed in the browser.
---

Panda is a compiler for your design system. Tokens, recipes, and styles go in as typed TypeScript. Atomic CSS comes out
at build time. Nothing computes or injects styles in the browser.

That last part is table stakes now. Several libraries generate CSS at build time. What Panda adds is a design system the
compiler enforces: your tokens and variants are types, a wrong value is a type error, and you can publish the whole
system as a package other apps consume.

Not sure which API to reach for as a component grows? See [Thinking in Panda](/docs/overview/thinking-in-panda).

## Why the alternatives fall short

Runtime CSS-in-JS libraries like emotion and styled-components do their work in the browser. Every render serializes
styles and injects `<style>` tags. That costs main-thread time, and it adds a styling engine to your bundle. Under React
Server Components the model breaks: a client style engine can't run while the server renders.

The usual escape is a utility-class framework. That removes the runtime cost, and the ecosystem is large. The tradeoff
is where your constraints live. Class strings are just strings, so a token name is never checked. Write `text-teal-400`
instead of your brand token and nothing fails at build time. You find out in review, or in production. Component
variants usually mean reaching for a separate library.

Panda puts the constraint in the type system instead. Dark mode is one semantic token, not a second class on every
element:

```tsx
// utility classes: two values, repeated at every call site
<div className="text-gray-900 dark:text-white" />

// Panda: one token that already knows what it means
<div className={css({ color: 'text' })} />
```

You keep colocated, composable styles. Your app ships plain CSS.

## Your design system is the product

Panda earns its keep when styles have to stay consistent across a codebase, and then across several. You define each
design decision once, and everything refers to it.

**Tokens** name your raw values. **Semantic tokens** name intent, and can resolve differently per condition:

```ts filename="panda.config.ts"
theme: {
  tokens: {
    colors: { gray900: { value: '#111' }, white: { value: '#fff' } }
  },
  semanticTokens: {
    colors: {
      text: { value: { base: '{colors.gray900}', _dark: '{colors.white}' } }
    }
  }
}
```

`css({ color: 'text' })` is now correct in both themes, and the hex lives in one place. See
[tokens](/docs/theming/tokens).

**Recipes** package a component's variants once, so a button is a contract instead of a pile of conditionals:

```ts
import { cva } from '../styled-system/css'

const button = cva({
  base: { rounded: 'md', fontWeight: 'semibold' },
  variants: {
    size: { sm: { px: '3', py: '1.5' }, lg: { px: '5', py: '3' } },
    tone: { solid: { bg: 'accent', color: 'white' }, ghost: { color: 'accent' } }
  },
  defaultVariants: { size: 'sm', tone: 'solid' }
})
```

**The types come from your config.** Autocomplete offers your tokens, not every CSS value, and a typo fails while you
type:

```ts
css({ color: 'red.500' }) // ✅ valid
css({ color: 'rde.500' }) // ❌ type error
```

Turn on [`strictTokens`](/docs/concepts/writing-styles#stricttokens) and Panda also rejects raw values where a token
belongs, so the system holds when the deadline is tight. Recipe variants are typed too. Pull a component's prop types
straight from its recipe with `RecipeVariantProps`.

**And you can ship it.** `panda lib` bundles your tokens, recipes, and pre-extracted CSS into a package. Other apps opt
in with one line, `designSystem: '@acme/ds'`, and reuse the system without re-scanning your source. One design system,
many apps, one source of truth.

## Styles next to your markup

Styles live in the file that uses them. No separate stylesheet to open, no class name to invent and keep in sync.

```tsx
import { css } from '../styled-system/css'
import { circle, stack } from '../styled-system/patterns'

function Profile() {
  return (
    <div className={stack({ direction: 'row', p: '4', rounded: 'md', shadow: 'lg', bg: 'white' })}>
      <div className={circle({ size: '5rem', overflow: 'hidden' })}>
        <img src="/avatar.png" alt="" />
      </div>
      <div className={css({ mt: '4', fontSize: 'xl', fontWeight: 'semibold' })}>John Doe</div>
      <div className={css({ mt: '2', fontSize: 'sm', color: 'gray.600' })}>john@doe.com</div>
    </div>
  )
}
```

Some people think in class names, others in props. Panda does both, and they extract to the same atoms:

```tsx
<div className={css({ color: 'text', px: '4' })} />
<styled.div color="text" px="4" />
```

[Patterns](/docs/concepts/patterns) like `stack`, `grid`, and `circle` cover the layouts you write constantly.
[Conditions](/docs/concepts/conditional-styles) like `_hover`, `_dark`, and `md` are keys in the same object.

Panda reads what it can see at build time, so a value that only exists at runtime needs a CSS variable or the `[...]`
escape hatch. The [dynamic styling](/docs/guides/dynamic-styling) guide covers each pattern.

## CSS you can reason about

- **Atomic CSS that plateaus.** One class per property, value, and condition, shared everywhere.
  `css({ color: 'red.500' })` and `<styled.div color="red.500" />` resolve to the same `.c_red\.500` rule, emitted once.
  Your CSS grows with the number of distinct styles you write, not with the size of your codebase.
- **Predictable overrides.** Panda emits into [cascade layers](/docs/concepts/cascade-layers) in a fixed order, so a
  utility always beats a recipe no matter the import order. No specificity wars.
- **Only the CSS you use.** Opt into `optimize` and Panda drops unused tokens and keyframes, so design-system entries
  you never reference don't ship.
- **A runtime that can disappear.** The generated functions only join class names. Pre-render with RSC, Astro, or a
  bundler transform and static calls are replaced by their class names, so the runtime leaves your bundle.

## Fast, native builds

Panda compiles your styles with a Rust engine built on the [Oxc](https://oxc.rs) toolchain. It parses each file once,
with no TypeScript program in the hot path, so builds stay fast and the install stays small. The same engine compiles to
WebAssembly, which is how the playground runs Panda in your browser.

## Works with your stack

The same API works in React, Solid, Preact, Vue, Svelte, Qwik, Astro, and plain HTML. Wire it in with a
[bundler plugin](/docs/installation/vite) for Vite, webpack, Rollup, or PostCSS, or run the
[CLI](/docs/installation/cli). Panda also reads styles out of `.vue`, `.svelte`, and `.astro` files, and out of compiled
JSX.

## When Panda is the wrong fit

- **You're happy with utility classes.** If token drift isn't a real problem on your team, a utility framework has a
  bigger ecosystem, more component kits, and coding models that already write its class names well. Type safety alone
  doesn't justify migrating a working codebase.
- **You don't want a codegen step.** Panda generates a `styled-system` folder, and TypeScript needs it before types
  resolve. Most teams run `panda codegen` on install and forget it, but it is a real setup cost.
- **You need styles computed at runtime.** Panda is static-first. Values known only when the app runs go through CSS
  variables instead of arbitrary style generation.
- **You're writing plain HTML and CSS,** on a template-based framework like Rails or PHP, or you want zero JavaScript in
  your toolchain. Vanilla CSS keeps getting better.
