AI has made it ridiculously easy to build interfaces. You can describe a page, give an agent a few instructions, and
have something working in just a few minutes.

But getting AI to build something that actually fits into your existing design system? That's where the real challenge
is.

Ask it to build a new page, and you might end up with buttons that look slightly different, spacing that feels off, or a
bunch of hardcoded colors that weren't part of your design system.

And the more pages you generate, the messier things can get.

So how do you get AI to stop guessing and start following the same design rules as the rest of your app?

That's what we're going to explore in this tutorial.

We'll follow one small piece of a billing app called **Ledger**: the badge that shows whether an invoice is paid,
overdue, or failed. At each step, you'll see how the code an agent writes for that badge changes.

I tried this with **Ledger**, a small billing app. We'll start with a simple task of asking an agent to create an
invoice status badge. Next, we use the same setup to ask an agent to build a whole billing settings page. I'll show you
the Panda CSS setup, how we pointed the agent to it, and what happened when we added checks to catch mistakes.

The goal is a design system your AI agent can actually understand and follow the next time you ask it to create
something.

## Why AI agents ignore your design system

Here's the kind of badge an agent writes when it can't see your design system:

```tsx
<span className={css({ bg: '#fee2e2', color: '#b91c1c', px: '8px', py: '2px', rounded: '9999px', fontSize: '12px' })}>
  Failed
</span>
```

![A pale red rounded badge with the word Failed in dark red text](/blog/ai-agents-badge-hardcoded.png)

_The badge above, rendered: it looks fine, but every value in it is hardcoded._

From the code above, nothing is obviously broken. The badge renders, and the colors might even look right. However, the
values are hardcoded directly into the component. If you decide to change the app's color palette, this badge won't
automatically update to that color.

An agent can only work with the context it has. If the existing components use hardcoded values, those become examples
it'll copy. If your design decisions are hidden in Figma, or scattered across files the agent hasn't read, it has to
guess.

We need to make the intended styling choices easy to discover, easy to reuse, and harder to bypass.

## Step 1: Give the agent a system to copy

First, let's give the agent something better than raw color values to work with.

For an invoice status, `status.failed.bg` tells you what the color is for. `red.100` only tells you what it looks like.
Panda CSS supports this distinction through [semantic tokens](/docs/theming/tokens#semantic-tokens).

```ts filename="panda.config.ts"
import { defineConfig } from '@pandacss/dev'

export default defineConfig({
  // ...
  theme: {
    extend: {
      semanticTokens: {
        colors: {
          status: {
            failed: {
              bg: { value: '{colors.red.100}', description: 'Failed payment badge background' },
              fg: { value: '{colors.red.700}', description: 'Failed payment badge text' }
            }
            // paid, overdue, and draft follow the same shape
          }
        }
      }
    }
  }
})
```

> The `description` field is optional, but it could give your agent a clue as to when to use each token.

Then turn the badge into a [recipe](/docs/recipes/config-recipe), so the agent picks a status instead of picking colors:

```ts filename="theme/badge.ts"
import { defineRecipe } from '@pandacss/dev'

export const badge = defineRecipe({
  className: 'badge',
  description: 'Invoice status. Pick a status, never set badge colors by hand.',
  base: { px: '2', py: '0.5', rounded: 'full', fontSize: 'xs', fontWeight: 'medium' },
  variants: {
    status: {
      paid: { bg: 'status.paid.bg', color: 'status.paid.fg' },
      overdue: { bg: 'status.overdue.bg', color: 'status.overdue.fg' },
      failed: { bg: 'status.failed.bg', color: 'status.failed.fg' },
      draft: { bg: 'status.draft.bg', color: 'status.draft.fg' }
    }
  },
  // The status comes from invoice data at runtime, so generate CSS for every status
  staticCss: [{ status: ['*'] }]
})
```

Register it in your config:

```ts filename="panda.config.ts"
import { badge } from './theme/badge'

export default defineConfig({
  theme: {
    extend: {
      recipes: { badge }
      // ...
    }
  }
})
```

Now the badge is one line:

```tsx
<span className={badge({ status: 'failed' })}>Failed</span>
```

There's another step that's easy to overlook: update the existing UI to use the recipe too. Agents often take cues from
nearby code. This means, if your app still has three different handwritten badge implementations, you've left three
competing examples for it to follow.

In our example, if the pages use `badge()`, the agent will also use `badge()` too, without being told.

## Step 2: Help your agent find and use your design system

Having tokens and recipes in the project doesn't mean an agent will automatically look for them. We can make that much
more likely in three ways.

- **Give it your project rules:** Add a short styling section to `AGENTS.md` (or `CLAUDE.md`, or whatever file your
  agent reads first)

```md filename="AGENTS.md"
## Styling

- Use the recipes in `styled-system/recipes` (`badge`, `button`, `card`, `input`). Don't style these by hand.
- Use semantic tokens like `status.failed.bg` and `fg.muted`. Never write hex colors, px values, or inline styles.
- If a token you need doesn't exist, stop and say so. Don't invent one.
```

- **Use Panda's agent skills:** These teach the agent how Panda works, like where to find your token names. Install
  them:

```bash
npx skills add chakra-ui/panda
```

Read more in the [Agent Skills docs](/docs/get-started/agent-skills).

- **Install the Panda MCP server:** This lets the agent look up the tokens and recipes that exist in your project right
  now. Add it to `.mcp.json` in your project root:

```json filename=".mcp.json"
{
  "mcpServers": {
    "panda": {
      "command": "npx",
      "args": ["-y", "@pandacss/mcp"]
    }
  }
}
```

Read more in the [MCP Server docs](/docs/get-started/mcp-server), including the config path for Cursor, VS Code, and
other clients.

## Step 3: Catch styling mistakes before they ship

Panda's `strictTokens` setting tightens the accepted values for token-backed style properties. Turn on
[`strictTokens`](/docs/reference/config#stricttokens) in your config:

```ts filename="panda.config.ts"
export default defineConfig({
  strictTokens: true
  // ...
})
```

Now a hardcoded value on a property that has tokens is a TypeScript error. The original badge, with `'#fee2e2'` and
`'8px'`, no longer compiles.

Then add the [Panda ESLint plugin](/docs/get-started/linting), which checks your code against your actual tokens:

```js filename="eslint.config.mjs"
import panda from '@pandacss/eslint-plugin'

const pandaConfig = await panda.configs.recommended({ configPath: './panda.config.ts' })

export default [
  // ...your existing config
  {
    ...pandaConfig,
    rules: {
      ...pandaConfig.rules,
      '@pandacss/prefer-token': ['error', { categories: ['colors', 'spacing', 'radii', 'fontSizes'] }]
    }
  }
]
```

Run it on the original badge and the lint output might look like this:

```txt
error  Hardcoded colors value "#fee2e2". Matching tokens: red.100, status.failed.bg (themed)
error  Hardcoded spacing value "8px". Matching tokens: 2
error  Hardcoded radii value "9999px". Matching tokens: full
error  Hardcoded fontSizes value "12px". Matching tokens: xs
```

When a hardcoded value exactly matches an existing token, the rule can suggest a replacement. For example, Ledger
defines `red.100` as `#fee2e2`. A similar looking value that doesn't match a token won't necessarily get the same
helpful suggestion.

### Run the checks automatically

Checks only help if they run. Add a line to `AGENTS.md` asking the agent to run them before it finishes:

```md filename="AGENTS.md"
- Before you say you're done, run the type check and the linter (`tsc --noEmit` and `eslint .`) and fix every error.
```

Then run the same commands in CI, so nothing outside the system merges, whether a person or an agent wrote it. If you
use Claude Code, a [hook](https://code.claude.com/docs/en/hooks) can also lint every file the agent edits and send the
errors straight back to it.

## Putting it to the test: Does the AI actually follow the design system?

So, we've set up our tokens, created reusable recipes, given the agent instructions, and added checks to catch mistakes.

But does all of this actually make a difference in the code AI generates?

To find out, we ran a small experiment using Claude Code (Sonnet 5.5) and our Ledger app.

We gave the agent the same task three times before setting up the design system rules, and three more times afterward.

The prompt was: **Build a billing settings page that matches the rest of the app.**

For each page the agent built, we counted the hardcoded hex colors in the code (values like `#fecaca` instead of a
token):

| Attempt | Before the setup | After the setup |
| :------ | :--------------- | :-------------- |
| 1       | 11               | 0               |
| 2       | 20               | 0               |
| 3       | 17               | 0               |

After the changes, the agent used the existing recipes for every badge, button, card, and input it created.

And here's the interesting part: **at a glance, the pages looked very similar.**

**Before: Hardcoded styles everywhere**

![Billing settings page generated before adding design system rules](/blog/ai-design-system-billing-before.png)

_Before: the billing page the agent built with no design system to follow. Note the darker cancel button, the heavier
text, and the invoice list outside a card._

```tsx
<section
  className={css({
    bg: 'white',
    border: '1px solid #fecaca',
    borderRadius: '8px',
    padding: '20px 24px'
  })}
>
  <h2
    className={css({
      fontSize: '14px',
      fontWeight: 600,
      marginBottom: '12px',
      color: '#b91c1c'
    })}
  >
    Danger zone
  </h2>
  {/* ... */}
  <button
    className={css({
      bg: '#b91c1c',
      color: 'white',
      px: '4',
      py: '2',
      rounded: 'md',
      fontSize: 'sm'
    })}
  >
    Cancel subscription
  </button>
</section>
```

The agent made all the styling decisions itself. It chose the colors, spacing, border radius, and typography.

It even introduced a new red, `#fecaca`, that wasn't used anywhere else in the app, and gave the cancel button
`#b91c1c`, a red the app only used for badge text.

Now compare that with what it generated after we set everything up.

**After: Using existing tokens and recipes**

![Billing settings page generated after adding design system rules](/blog/ai-design-system-billing-after.png)

_After: the billing page the agent built with tokens, recipes, rules, and checks in place._

```tsx
<section className={card({ tone: 'danger' })}>
  <h2
    className={css({
      textStyle: 'sectionTitle',
      color: 'fg.danger',
      mb: '3'
    })}
  >
    Danger zone
  </h2>
  {/* ... */}
  <button className={button({ variant: 'danger' })}>Cancel subscription</button>
</section>
```

Instead of defining everything from scratch, the agent reused the `card` and `button` recipes we already created. It
also used our typography and color tokens.

## Give it a try in your own project

You don't need to set up everything at once. You can start with the
[Panda agent skills](/docs/get-started/agent-skills):

```bash
npx skills add chakra-ui/panda
```

Then give your agent a task and read the code it writes. If it still invents styles you've already defined, add the
project rules, the [Panda MCP server](/docs/get-started/mcp-server), and [linting](/docs/get-started/linting).
